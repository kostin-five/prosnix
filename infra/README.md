# Инфраструктура Prosnix

Приложение развёртывается как модульный монолит:

- `apps/web` — статический сайт, доступный по HTTPS;
- запросы `/api/*` перенаправляются серверу `apps/api` через адрес сайта;
- PostgreSQL хранит исходные наблюдения и настройки.

Текущая схема размещения — Render Static Site, Render Web Service, Neon PostgreSQL
и внешний планировщик cron-job.org. Подробности — в [руководстве по эксплуатации](../docs/operations.md).

## Среды

Разработка, предварительная проверка и рабочее приложение должны использовать отдельные БД,
секреты и настройки Telegram. В рабочей среде запрещены примеры секретов из `.env.example`.
Фактическое разделение сред нужно проверить перед выпуском: наличие этого требования в документации
не означает, что отдельные ресурсы уже созданы.

## Локальная база данных

```bash
pnpm db:start
pnpm db:migrate
```

Остановка: `pnpm db:stop`. Именованный том Docker сохраняет данные после обычной остановки.
Если порт `5432` занят, используйте другой порт и тот же адрес в настройках БД:

```bash
POSTGRES_PORT=55432 pnpm db:start
DATABASE_URL=postgres://awc:awc@localhost:55432/awc pnpm db:migrate
```

Эти значения предназначены только для локальной разработки.

## Совместимость схемы и откат

Миграция должна оставаться совместимой с предыдущей версией приложения:

1. Сначала добавляйте поля, таблицы и индексы, не удаляя прежние структуры.
2. Разверните код, который умеет читать обе версии схемы.
3. Перенесите данные отдельной контролируемой операцией.
4. Удаляйте прежние поля в следующем выпуске после проверки возможности отката.

Перед выпуском проверьте миграцию на отдельной тестовой БД и запуск предыдущей версии приложения.
Откат кода не должен откатывать уже применённую схему.

## Резервное копирование

Рабочая PostgreSQL должна поддерживать шифрованное подключение, резервные копии
и восстановление на выбранный момент времени в пределах возможностей тарифа.

Проверка восстановления выполняется в новой изолированной БД:

1. Создайте резервную копию и запишите её время и идентификатор.
2. Восстановите её в отдельную базу.
3. Примените текущие миграции.
4. Проверьте `/health`, начальную загрузку, продолжение сессии и аналитику.
5. Сверьте число пользователей, сессий и наблюдений. Не включайте секреты и ответы в отчёт.
6. Удаляйте тестовую базу только после фиксации результата и с разрешения владельца.

## Плановая отправка Telegram

cron-job.org раз в пять минут отправляет `POST /internal/notifications/dispatch`
с заголовком `Authorization: Bearer <CRON_SECRET>`, типом `application/json` и телом `{}`.
Планировщику не передаются строка подключения к БД и токен Telegram.

API резервирует ожидающие отправки в PostgreSQL, выполняет ограниченные повторные попытки
и удаляет технические журналы доставки старше 90 дней. Оценки пользователя и сессии сохраняются.
Параллельный запуск отправки в одном процессе получает `409`.
