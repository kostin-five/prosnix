# План реализации: Follow-up и эксплуатационная надёжность

**Ветка**: `dev` | **Дата**: 2026-08-30 | **Спецификация**: [spec.md](./spec.md)

## Краткое описание

Расширить существующий контур Telegram-доставки вторым типом сообщения для завершённых сессий без
follow-up. Добавить отдельный журнал follow-up доставок, сводную обработку обоих типов, защиту от
пересекающихся HTTP-запусков и очистку технических журналов старше 90 дней. Существующий интерфейс
ответа и аналитика не меняются.

## Технический контекст

**Язык/версия**: TypeScript 5.9, Node.js 22

**Основные зависимости**: Fastify 5, Drizzle ORM, PostgreSQL 17, Telegram Bot API

**Хранение**: Neon PostgreSQL; новая append-oriented таблица follow-up доставок и forward-only
миграция

**Тестирование**: Vitest unit/contract, PostgreSQL integration, существующий Playwright smoke

**Целевая платформа**: stateless Render API; cron-job.org вызывает один защищённый endpoint каждые
пять минут

**Тип проекта**: TypeScript pnpm workspace, модульный монолит

**Цели производительности**: один HTTP-запуск обрабатывает суммарно до 20 доставок менее чем за 30
секунд; до пяти параллельных Telegram-запросов на тип

**Ограничения**: at-most-once при неопределённом ответе Telegram; follow-up не позже 60 минут;
секреты только на сервере; cron body не содержит пользовательских параметров

**Масштаб этапа**: пилот до 10 000 пользователей и 2 000 сообщений в день

## Архитектура и поток данных

1. Завершение протокола уже сохраняет `follow_up_due_at = completed_at + 15 минут`.
2. Планировщик вызывает существующий защищённый POST endpoint без пользовательских параметров.
3. Репозиторий атомарно выбирает завершённые сессии с наступившим сроком и без follow-up ответа.
4. Уникальность по `session_id` и конфликтобезопасная вставка исключают повторную доставку.
5. Перед отправкой репозиторий повторно проверяет отсутствие ответа; при гонке доставка становится
   `skipped`, а сообщение не уходит.
6. Telegram adapter выбирает текст и кнопку по `kind: wake | follow_up`; секрет и URL остаются
   общими серверными зависимостями.
7. Результаты утренних и follow-up сообщений возвращаются раздельно и суммарно, вместе с задержкой
   и длительностью запуска.
8. В конце успешного запуска удаляются оба типа журналов с `created_at < now - 90 дней`.

## Границы доверия и защита

- Bearer-секрет сравнивается константным по данным способом и не логируется.
- Endpoint не принимает user/session/chat ID, срок или тип сообщения из тела.
- Один процесс не допускает пересекающийся run; конкурентные процессы всё равно защищены
  уникальными ключами и условными update.
- Сводка содержит только счётчики, миллисекунды задержки/работы и количество удалённых строк.
- Telegram ID используется только внутри DB adapter и gateway.

## Надёжность, миграции и откат

- Миграция только добавляет таблицу и индексы; текущие ежедневные напоминания продолжают работать
  во время rolling deploy.
- Follow-up delivery имеет уникальный `session_id`, максимум две попытки и те же terminal states.
- Опоздание свыше 60 минут сохраняется как `skipped`, чтобы не беспокоить пользователя позже.
- Неизвестный network/5xx результат terminal (`ambiguous`) и не повторяется автоматически.
- Откат к предыдущему API оставляет новую таблицу неиспользуемой; удаление выполняется только
  отдельной будущей миграцией.
- Ошибка очистки делает весь служебный запрос неуспешным, чтобы cron-job.org отправил оповещение;
  повтор безопасен.

## Наблюдаемость

- События включают тип `wake|follow_up`, результат `sent|skipped|failed`, агрегированный completion
  и cleanup.
- HTTP response содержит `wake`, `followUp`, `total`, `maintenance`, `durationMs` и `maxLagMs`.
- cron-job.org сохраняет код ответа и может уведомлять после двух последовательных ошибок.
- Токены, chat ID, содержимое follow-up и Telegram response body исключены.

## Отслеживание сложности

Новые внешние сервисы, Redis и очередь не добавляются. Вторая delivery-таблица выбрана вместо
полиморфной миграции проверенной таблицы, чтобы rollout и rollback оставались безопасными.
