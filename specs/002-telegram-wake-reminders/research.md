# Исследование: Telegram-напоминания о пробуждении

## Решение 1: Telegram-напоминание, а не системный будильник

**Решение**: называть функцию напоминанием и явно сообщать о зависимости от настроек Telegram,
устройства, сети и режима «Не беспокоить».

**Почему**: Mini App работает внутри Telegram и не может обещать системный alarm, обязательный звук
или обход ограничений ОС.

**Рассмотрено**: Web Push и нативный будильник отложены — они требуют другого канала доставки и
разрешений, которых нет у текущего Mini App.

**Источник**: https://core.telegram.org/bots/webapps

## Решение 2: Сообщение бота с Web App кнопкой

**Решение**: отправлять личное сообщение через `sendMessage` и `InlineKeyboardButton.web_app` на
публичный HTTPS URL приложения.

**Почему**: это официальный путь вернуть пользователя из чата непосредственно в Mini App. Бот не
может первым начать диалог, поэтому доступность чата проверяется фактической доставкой.

**Рассмотрено**: обычная URL-кнопка остаётся запасным вариантом, но Web App кнопка лучше сохраняет
контекст Telegram.

**Источник**: https://core.telegram.org/bots/api#inlinekeyboardbutton

## Решение 3: Защищённый HTTP-триггер cron-job.org

**Решение**: cron-job.org каждые пять минут отправляет POST-запрос на внутренний endpoint Render
API. Запрос авторизуется отдельным Bearer-секретом, а endpoint сам читает due-записи из Neon.

**Почему**: платный Render Cron Job не нужен для пилота, а таймер внутри засыпающего HTTP-процесса
ненадёжен. Внешний сервис выполняет только роль часов и не получает доступ к БД или токену бота.
Лимит десять доставок и параллельность пять удерживают активную обработку в пределах HTTP timeout.

**Рассмотрено**: Render Cron Job требует платного сервиса; постоянный background worker дороже;
публичный endpoint без отдельной авторизации неприемлем.

**Источник**: https://docs.cron-job.org/rest-api.html

## Решение 4: PostgreSQL как очередь текущего масштаба

**Решение**: использовать таблицу доставок, уникальный индекс и `FOR UPDATE SKIP LOCKED`.

**Почему**: это даёт атомарное резервирование несколькими процессами без Redis и согласуется с
существующим источником истины.

**Рассмотрено**: Redis/BullMQ и managed queue отложены до измеренной нагрузки или требований к
доставке чаще одной минуты.

**Источник**: https://www.postgresql.org/docs/current/sql-select.html

## Решение 5: Безопасный повтор

**Решение**: автоматически повторять только явный `429` с `retry_after`. Не повторять timeout и
5xx, потому что неизвестно, принял ли Telegram сообщение. Следующее ежедневное срабатывание не
блокируется.

**Почему**: Telegram Bot API не предоставляет клиентский idempotency key для `sendMessage`.
At-most-once предпочтительнее двойного утреннего сообщения.

**Рассмотрено**: повтор всех временных ошибок повышает доставляемость, но нарушает ключевое
требование отсутствия дублей.

**Источник**: https://core.telegram.org/bots/api#making-requests

## Решение 6: Следующий момент хранится в UTC

**Решение**: сохранять `HH:mm`, IANA timezone и вычисленный `next_trigger_at` в UTC. После каждого
резервирования рассчитывать следующий локальный день.

**Почему**: due-query остаётся простой и индексируемой, а пользовательское время корректно следует
за DST и сменой часового пояса.

**Рассмотрено**: хранить только cron-выражение недостаточно для пользовательских timezone и
неоднозначного времени при переводе часов.

**Источник**: https://www.iana.org/time-zones
