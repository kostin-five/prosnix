# План реализации: Telegram-напоминания о пробуждении

**Ветка**: `dev` | **Дата**: 2026-08-29 | **Спецификация**: [spec.md](./spec.md)

## Краткое описание

Добавить к существующему модульному монолиту серверное ежедневное расписание, журнал отдельных
доставок и одноразовый обработчик очереди, который можно запускать защищённым HTTP-триггером. Mini App
читает и меняет настройку через авторизованный API. Telegram-адаптер получает только уже
зарезервированную доставку и не участвует в доменных расчётах времени.

## Технический контекст

**Язык/версия**: TypeScript 5.9, Node.js 22

**Основные зависимости**: React 18, Vite 6, Fastify 5, TypeBox, Drizzle ORM, PostgreSQL 17,
Telegram Bot API

**Хранение**: существующий Neon PostgreSQL; две новые таблицы с каскадным удалением

**Тестирование**: Vitest для домена и API, PostgreSQL integration tests, Playwright для UI

**Целевая платформа**: Telegram Mini App и stateless Render Web Service; cron-job.org каждые пять
минут вызывает защищённый внутренний endpoint одноразовой обработки доставок

**Тип проекта**: TypeScript pnpm workspace, модульный монолит

**Цели производительности**: чтение/изменение расписания p95 < 500 мс; один запуск обработчика
разбирает до 100 доставок; пользовательское окно доставки — не более пяти минут

**Ограничения**: одно расписание на пользователя; IANA timezone; UTC timestamps; Telegram не
гарантирует звук; нельзя повторять запрос с неопределённым результатом; секреты бота и cron только
на API-сервере; внешний планировщик получает только отдельный `CRON_SECRET`

**Масштаб этапа**: пилот до 10 000 пользователей и 1 000 активных расписаний в день

**Решение по структуре**: сохранить существующие границы workspace. Новый доменный модуль отвечает
за валидацию расписания и вычисление следующего UTC-момента. DB-пакет атомарно резервирует
доставки. API предоставляет пользовательский контракт, Telegram-адаптер и одноразовый worker.

## Архитектура и поток данных

1. Авторизованный пользователь читает `GET /api/v1/me/wake-schedule`.
2. `PUT /api/v1/me/wake-schedule` проверяет `HH:mm`, IANA timezone и сохраняет ровно одну настройку.
3. При включении или изменении рассчитывается следующий реальный UTC-момент выбранного локального
   времени. При переходе часов назад сохраняется только один ближайший момент.
4. cron-job.org отправляет `POST /internal/notifications/dispatch` с отдельным Bearer-секретом.
   Endpoint обрабатывает не более десяти доставок с ограниченной параллельностью и не принимает
   идентификаторы пользователей или расписаний извне.
5. Репозиторий в транзакции создаёт уникальную доставку для наступившей даты, переводит её в
   состояние `sending` и сразу рассчитывает следующую дату расписания.
6. Worker вызывает Telegram `sendMessage` с приватным `chat_id` и кнопкой `web_app`.
7. Успех фиксирует `message_id`; постоянный отказ помечает бота заблокированным; только явный
   ответ Telegram `429` может быть повторён после `retry_after`. Сетевой timeout и 5xx считаются
   неопределённым исходом и автоматически не повторяются, чтобы не разбудить дважды.
8. Bootstrap возвращает расписание, чтобы главный экран не выполнял отдельный каскадный запрос.

## Границы доверия и секреты

- Пользовательский `user_id` берётся только из подписанной HTTP-only сессии.
- `TELEGRAM_BOT_TOKEN`, `DATABASE_URL` и подключение Neon существуют только в Render Web Service.
- cron-job.org хранит только `CRON_SECRET`; этот секрет отличается от токена Telegram.
- Endpoint не принимает Telegram ID, дату доставки или расписание из HTTP-запроса.
- Сравнение Bearer-секрета выполняется безопасно, значение не попадает в логи и тело ответа.
- В журнале ошибок сохраняются категория и код, но не токен, полный ответ Telegram или текст
  пользовательских данных.
- URL Mini App задаётся отдельной серверной переменной и проверяется как HTTPS в production.

## Надёжность, миграции и откат

- Уникальный индекс `(schedule_user_id, scheduled_for)` не допускает две записи одного срабатывания.
- Транзакционная блокировка с `SKIP LOCKED` распределяет работу между параллельными worker без
  общей памяти и Redis.
- Доставка старше 15 минут помечается пропущенной, а расписание продвигается вперёд.
- Миграция только добавляет таблицы и nullable-поле bootstrap-контракта, поэтому предыдущая версия
  API продолжит работать во время отката.
- Откат приложения оставляет новые таблицы нетронутыми; удалять их следует отдельной миграцией
  только после подтверждения.
- Neon backups/PITR и Render health checks остаются базой восстановления.

## Наблюдаемость

- Структурные события: `wake_schedule.updated`, `notification.claimed`, `notification.sent`,
  `notification.failed`, `notification.skipped`.
- Метрики: задержка от `scheduled_for`, число due/claimed/sent/blocked/ambiguous, длительность run.
- Корреляция по внутренним UUID; Telegram ID, bot token и текст сообщения в лог не попадают.
- Worker завершается ненулевым кодом при системной ошибке до обработки, но ошибка одной доставки
  не останавливает остальные.

## Проверка конституции после проектирования

Все пять принципов остаются соблюдены. Отдельный брокер сообщений не нужен: PostgreSQL уже
обеспечивает транзакции и блокировки для текущего масштаба. Ограничение at-most-once при
неопределённом ответе Telegram выбрано осознанно — возможная пропущенная доставка безопаснее
двойной. Статус **PASS**.

## Отслеживание сложности

Дополнительные сервисы, Redis и постоянный background worker не вводятся. cron-job.org — только
внешний таймер для защищённого endpoint; PostgreSQL остаётся источником истины и очередью.
