# Исследование: Релизное усиление MVP

## Production-зависимости

**Решение**: удалить неиспользуемый `react-router` и обновить `drizzle-orm` с 0.44.7 до 0.45.2.

**Обоснование**: `pnpm audit --prod` обнаружил 13 advisory: одну high для Drizzle и двенадцать для
React Router. Поиск импортов подтвердил, что React Router не используется: публичная политика
выбирается по `window.location.pathname`. Для Drizzle 0.45.2 является первой исправленной версией;
точечное обновление уменьшает риск несовместимости.

**Рассмотренные альтернативы**: обновить React Router до последней версии — отклонено как сохранение
ненужной поверхности атаки; массово обновить все пакеты — отклонено как трудно проверяемое изменение.

## Защитные HTTP-границы

**Решение**: официальные Fastify helmet/rate-limit плагины, глобальный body limit 32 КиБ, отдельные
низкие лимиты для Telegram auth и AI Coach, `Cache-Control: no-store` для API.

**Обоснование**: плагины соответствуют lifecycle Fastify и уменьшают объём собственного security
кода. Wake-session запросы частые, поэтому глобальный rate-limit не применяется; ограничиваются
только границы, которые проверяют подпись или потенциально вызывают внешний AI.

**Рассмотренные альтернативы**: самописный Map limiter — хуже протестирован и сложнее корректно
очищается; Redis — преждевременная инфраструктура для одного instance.

## Liveness, readiness и завершение

**Решение**: `/health` проверяет процесс, `/ready` выполняет ограниченный `select 1`; SIGTERM/SIGINT
закрывают Fastify и DB через одну идемпотентную функцию с deadline.

**Обоснование**: liveness не должна перезапускать живой процесс из-за краткого сбоя БД, readiness не
должна направлять трафик в экземпляр без хранилища. Render поддерживает отдельный health path.

**Рассмотренные альтернативы**: заменить `/health` DB-проверкой — смешивает две семантики и может
создать restart loop; проверять все внешние сервисы — DeepSeek и Telegram имеют fallback и не
блокируют основной путь.

## CI и dependency updates

**Решение**: один обязательный verify job с PostgreSQL и E2E, отдельный security audit job,
concurrency cancellation, Playwright report при ошибке и еженедельные малые Dependabot PR.

**Обоснование**: основной pipeline уже покрывает критический путь. Усиление сохраняет понятный gate,
не дублируя дорогие тесты, и делает ошибки диагностируемыми.

**Рассмотренные альтернативы**: автоматический deploy из GitHub Actions — отклонён, потому что
Render уже владеет deploy из `dev`, а второй источник создаст гонки; автоматическое слияние
Dependabot — отклонено до закрытой беты.
