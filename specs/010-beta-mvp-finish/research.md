# Исследование решений: Финальная Beta-версия MVP

## Решение 1: локальный SVG-wordmark вместо баннера

- **Решение**: использовать семантический React/SVG wordmark в цветовых токенах приложения.
- **Обоснование**: полный баннер имеет неподходящее соотношение сторон и добавит лишний raster request; SVG остаётся резким и доступным.
- **Альтернативы**: обрезанный PNG (хуже адаптируется), обычный текст (не решает фирменность).

## Решение 2: серверный дневной ряд на главной

- **Решение**: главная показывает `dailyTrend`, а не повторно группирует последние history items.
- **Обоснование**: сервер уже учитывает timezone, парность оценок и несколько сессий в день; это устраняет расхождение экранов.
- **Альтернативы**: исправить только CSS текущих session bars (видно, но остаётся неверная семантика «по дням»).

## Решение 3: подтверждение раннего AI-запроса в том же endpoint

- **Решение**: optional `confirmEarly` и статус `confirmation_required`.
- **Обоснование**: подтверждение проверяется сервером, не требует новой сущности или endpoint и обратно совместимо для 3+ сессий.
- **Альтернативы**: только клиентский modal (можно обойти), полный запрет до трёх сессий (противоречит выбору пользователя).

## Решение 4: глубокий отчёт без изменения таблицы кэша

- **Решение**: сохранить `summary`, `nextExperiment`, `caveat`, но изменить их смысл и prompt.
- **Обоснование**: даёт полезный результат без миграции и сохраняет дневной кэш; UI может назвать части понятнее.
- **Альтернативы**: новый JSONB report schema (избыточен перед MVP), свободный markdown (сложнее валидировать).

## Решение 5: детерминированные trend signals

- **Решение**: service считает направление и вариативность из `dailyTrend`, округляет значения и отправляет только агрегаты.
- **Обоснование**: AI получает новую аналитическую опору без сырых сессий; fallback использует те же сигналы.
- **Альтернативы**: отправлять историю (нарушает минимизацию), просить модель самой вывести сигналы из UUID/timestamps (лишние данные).
