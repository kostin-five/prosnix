# Безопасность Prosnix

## Как сообщить об уязвимости

Не создавайте публичный issue с уязвимостью или секретами. Свяжитесь с владельцем репозитория через
приватный канал, указанный в профиле проекта/боте `@prosnix_bot`.

Сообщение должно содержать:

- затронутую версию/commit и среду;
- безопасные шаги воспроизведения;
- ожидаемое и фактическое поведение;
- оценку влияния без реальных пользовательских данных;
- возможное исправление, если оно известно.

Не присылайте bot token, `.env`, `DATABASE_URL`, cookie, Telegram `initData`, webhook/cron secret,
DeepSeek key, payment update целиком или персональные ответы. Не выполняйте destructive proof of
concept и не извлекайте больше данных, чем необходимо для подтверждения проблемы.

Владелец подтверждает получение, определяет severity и согласует безопасное исправление/release.
Публичное раскрытие возможно только после выпуска исправления и явного согласования.

## Поддерживаемая версия

Пока нет стабильных release tags, security fixes применяются к актуальной ветке `dev`. Перед
публичным MVP политика версий должна быть пересмотрена вместе с release branching.

## Обязательные правила

- Secrets находятся только в local `.env` или server-side secret manager/Render Environment.
- `VITE_*` всегда считается публичным.
- Telegram `initData` проверяется сервером текущим bot token и ограничивается по возрасту.
- Персональные API требуют подписанную `HttpOnly` cookie; admin — server allowlist.
- DB доступна только API/repository/migration layer; production DB не используется в тестах.
- Все API/internal/health ответы имеют `Cache-Control: no-store`; payload ограничен 32 КиБ.
- Auth, coach и billing имеют rate limits; расширение защиты требует измерений и ADR при новом
  инфраструктурном механизме.
- AI получает только минимальный агрегированный контекст и не является source of truth.
- Webhook/cron используют разные secrets; сравнение выполняется безопасно.
- Платежи и повторяемые state changes идемпотентны.
- Логи не содержат authentication material или пользовательские ответы.
- Dependency audit, bundle boundary и production boundary являются release gates.

## Работа с инцидентом

1. Не удалять логи/данные и не делать непроверенный rollback schema.
2. Ограничить затронутую функцию самым обратимым способом: например, выключить billing ценой `0`.
3. Ротировать скомпрометированный secret в его системе и обновить только нужный consumer.
4. Проверить Render logs/audit events по request/correlation ID без раскрытия payload.
5. Выпустить regression test и исправление через обязательный CI.
6. При rollback откатить код на совместимый deploy, не откатывая forward-only migration.
7. Зафиксировать timeline, влияние и дальнейшие меры без персональных данных.

Production mutation, ротация secret, webhook, удаление данных и уведомление пользователей требуют
явного решения владельца и соблюдения применимых обязанностей.
