# Эксплуатация Prosnix

Здесь описаны проверка приложения, развёртывание, диагностика и откат.
Первоначальная настройка — в [инструкции Telegram Mini App](telegram-mini-app-setup.md).
Наличие коммита на GitHub не означает, что приложение уже обновлено на хостинге.

## Где управлять компонентами

| Компонент      | Панель                         | Содержимое                                         |
| -------------- | ------------------------------ | -------------------------------------------------- |
| Код и проверки | GitHub, ветки `dev` и `master` | Исходники и сценарии проверок, без секретов        |
| API            | Render Web Service             | Серверное приложение и переменные окружения        |
| Клиент         | Render Static Site             | Собранное приложение React, без серверных секретов |
| БД             | Neon                           | Пользователи, сессии, расписания и кэш отчётов     |
| Бот            | BotFather                      | Настройки бота и выпуск токена                     |
| Планировщик    | cron-job.org                   | Адрес отправки и отдельный секрет `CRON_SECRET`    |

## Перед развёртыванием

1. Проверьте ветку `dev` и отсутствие случайных файлов в `git status`.
2. Подготовьте отдельную локальную тестовую PostgreSQL и выполните
   `pnpm verify:release:full` по [руководству тестирования](testing.md).
   Обычную рабочую БД использовать нельзя: имя тестовой базы должно содержать `test`.
3. Проверьте отсутствие уязвимостей высокой или критической степени.
4. Отправьте коммит в `origin/dev` и дождитесь всех проверок GitHub Actions для точного SHA.
5. Получите разрешение владельца на выпуск. При выключенном автоматическом развёртывании
   запустите его вручную и сверьте выбранный SHA.

## Порядок развёртывания

1. Установите зависимости, соберите API и примените новые миграции с разрешения владельца.
2. Проверьте резервную копию перед изменением рабочей БД. Миграции применяются только вперёд.
3. Дождитесь запуска API и успешного ответа `/ready` с подключённой БД.
4. Опубликуйте статический сайт совместимой версии. Сохраните перенаправление `/api/*`,
   `/health` и `/ready` на API.
5. Проверьте приложение в Telegram.

Рекомендуемый путь проверки готовности Render — `/ready`. `/health` проверяет только процесс.
При завершении старого процесса API обрабатывает SIGTERM и закрывает соединения
в пределах настроенного времени.

## Краткая проверка после обновления

Адреса ниже соответствуют описанной конфигурации проекта; перед выпуском сверьте их с хостингом.

```bash
curl --fail --silent https://wake-coach.onrender.com/health
curl --fail --silent https://wake-coach.onrender.com/ready
curl --fail --silent https://wake-coach-1.onrender.com/ready
```

В Telegram откройте настроенного бота и проверьте:

- вход и загрузку главной;
- создание сессии, запись шага и продолжение после закрытия мини-приложения;
- завершение, итоговую оценку, статистику и историю;
- расписание и однократное откладывание напоминания;
- повторную проверку через 15–20 минут для отдельной тестовой сессии.

## Резервные копии Neon

Включите доступные тарифу резервное копирование и восстановление на выбранный момент времени.
Перед рискованной миграцией создайте отдельную ветку БД или точку восстановления.

Не восстанавливайте копию поверх предварительной или рабочей среды ради проверки.
Создайте отдельную временную БД, сверьте таблицы и проверьте тестовый API.
Не публикуйте строку подключения в результатах GitHub Actions или сообщениях.
Удаляйте временную БД после фиксации результата и с разрешения владельца.

Рекомендуемая ежемесячная проверка — восстановить отдельную БД, применить миграции,
запустить интеграционные тесты и записать результат без пользовательских данных.
Ограничения запуска тестов на БД описаны в [руководстве](testing.md).

## Административная панель

1. В переменных API-сервиса Render укажите в `ADMIN_TELEGRAM_USER_IDS` числовой Telegram ID,
   а не имя пользователя. Не публикуйте его вместе с данными аккаунта.
2. Настройте основное мини-приложение в BotFather.
3. Откройте `https://t.me/prosnix_bot?startapp=admin` из нужного аккаунта Telegram.
4. Проверьте периоды 7/30/90 дней. Доступны только агрегаты, без индивидуальных оценок и UUID.

Если панель закрыта, проверьте список разрешённых пользователей и аккаунт запуска.
Обычный пользователь должен получать закрытый ответ.
Если разрешённая панель не загружает метрики, найдите показанный «Код запроса» в журналах Render.
Не копируйте cookie, `initData`, окружение сервера и строку подключения.

Обычная вкладка браузера не передаёт данные запуска Telegram. Ссылка запуска может открыть
приложение в Telegram, но не предоставляет браузеру административный доступ.
Ответ `404` для пользователя без разрешения ожидаем.

## Диагностика

### `/health` работает, `/ready` возвращает 503

Найдите `requestId` и событие `readiness_failed` в журналах Render.
Проверьте наличие `DATABASE_URL`, состояние Neon и лимит соединений.
После исправления дождитесь `200 {"status":"ready"}` перед проверкой Telegram.
Строку подключения не публикуйте.

### Ошибка 500 в административной панели

Найдите безопасный код запроса в журнале.
`invalid input value for enum subscription_status: "past_due"` означает отсутствие значения
в старой схеме. Не редактируйте миграцию `0004`: после проверок и разрешения примените
`0009_subscription_status_repair`. Совместимое чтение `status::text` позволяет читать панель
до исправления, но не позволяет записывать отсутствующее значение.

`relation "telegram_star_payments" does not exist` при выключенных продажах указывает
на неполную старую схему. Панель должна вернуть нулевые платёжные агрегаты без чтения таблиц.
Не создавайте их вручную; перед включением оплаты проверьте всю схему.

### Приложение открывается, API отвечает 401

Проверьте запуск из Telegram, соответствие токена выбранному боту, часы сервера
и `TELEGRAM_AUTH_MAX_AGE_SECONDS`. Реальный `initData` нельзя помещать в публичный журнал.

### `429 rate_limit_exceeded`

Подождите минуту и повторите один раз. Если ошибка возникает при обычном использовании,
проверьте число экземпляров API и заголовки прокси Render.
Меняйте `AUTH_RATE_LIMIT_MAX` и `COACH_RATE_LIMIT_MAX` по результатам диагностики.
Нескольким экземплярам нужен общий механизм ограничения частоты запросов.

### Ошибки плановой отправки

- `401`: секрет в заголовке планировщика не совпадает с `CRON_SECRET` API.
- `415`: отсутствует `Content-Type: application/json` или тело `{}`.
- `409`: предыдущая отправка ещё выполняется; дождитесь следующего запуска.

## Безопасный откат

Выберите предыдущую рабочую версию сервиса Render. Не откатывайте применённые миграции
и не удаляйте таблицы. После отката проверьте `/health`, `/ready`, начальную загрузку
и тестовую сессию. При ошибке только статического сайта клиент можно откатить отдельно.
Запишите SHA, время, симптом и результат без секретов и ответов пользователей.

## Регулярные действия

- Ежедневно: проверка `/ready` и ошибок Render.
- Еженедельно: просмотр обновлений Dependabot и результатов CI.
- Ежемесячно: проверка восстановления и основных сценариев в Telegram на iOS, Android и компьютере.
- Перед рабочим выпуском: проверка разделения ботов, БД, сервисов, секретов и правовых реквизитов.
