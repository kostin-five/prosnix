# Стратегия тестирования Prosnix

## Цель

Тесты защищают источник истины: Telegram identity, session state, исходные наблюдения,
экспериментальные формулы, уведомления, legal acceptance и платежные события. Количество тестов само
по себе не является критерием готовности.

## Перед запуском

- Node.js 22–24 и pnpm 11.19.0;
- зависимости установлены через `pnpm install --frozen-lockfile`;
- для integration — отдельная PostgreSQL 17 с применёнными migrations;
- production/staging `DATABASE_URL` использовать запрещено;
- для E2E установить Chromium: `pnpm exec playwright install chromium`.

## Уровни

Обычный API `test` исключает integration-файлы; полный gate выполняет их отдельной командой.
Integration-файлы запускаются последовательно, поскольку сценарии уведомлений используют общую
тестовую очередь. Конкурентные запросы внутри специальных тестов продолжают выполняться параллельно.
Это устраняет перехват чужих тестовых уведомлений и повторный запуск БД-сценариев внутри unit gate.

Досрочное пробуждение проверяется на честные task observations, post-rating, idempotency, конфликт
версии, history, follow-up, отсутствие recovery и исключение из learning count/аналитики.
Настройка паузы проверяется на 5/10/20 секунд, сохранение выбранного значения, изоляцию пользователя
и остановку подготовки при скрытии. Mobile flow проверяет кнопку «Проснулся» слева от крестика на 320 px.

| Уровень        | Где                                                | Что проверяет                                               |
| -------------- | -------------------------------------------------- | ----------------------------------------------------------- |
| Domain unit    | `packages/domain/tests`                            | state machine, adaptive selector, analytics, timezone       |
| API contract   | `apps/api/tests/contract`                          | auth boundary, schemas, status codes, headers, rate limits  |
| Adapter unit   | `apps/api/tests/coach`, `notifications`, `runtime` | DeepSeek/Telegram mapping, fallback, dispatch, shutdown     |
| DB integration | `apps/api/tests/integration`                       | migrations, transactions, constraints, concurrency, cascade |
| Web component  | `apps/web/tests`                                   | tasks/legal/admin/settings UX и accessibility               |
| Mobile E2E     | `tests/e2e`                                        | critical journey в mobile Chromium                          |
| Static checks  | `scripts/verify-*`                                 | initial bundle и отсутствие server/test secrets в web build |

## Команды

Быстрый цикл:

```bash
pnpm format:check
pnpm typecheck
pnpm test
```

Сборка и production boundaries:

```bash
pnpm build
pnpm verify:web-bundle
pnpm verify:production
pnpm audit --prod --audit-level high
```

Интеграционные тесты:

```bash
pnpm db:start
pnpm db:migrate
pnpm test:integration
```

E2E:

```bash
pnpm test:e2e
```

Обязательный набор перед обычным merge:

```bash
pnpm verify:release
```

Полный release candidate при запущенной тестовой БД:

```bash
pnpm verify:release:full
```

## Правила добавления тестов

- Исправление бага сначала получает regression test на самом дешёвом надёжном уровне.
- Новая доменная формула получает фиксированный fixture и ручной ожидаемый результат.
- Adaptive selection проверяется на детерминизм, isolation контекста/бюджета, exploration,
  повторную проверку лучшего и запрет непосредственного exact-repeat.
- Пилотный возврат проверяется на границе ровно семи суток и отдельно учитывает pending-когорту.
- Новая запись API проверяет отсутствие idempotency key, повтор запроса и конфликт версии.
- Новая персональная выборка проверяет isolation двух пользователей и каскадное удаление.
- Новая внешняя интеграция проверяет timeout, некорректный ответ, повтор и безопасный fallback.
- Быстрый Telegram follow-up проверяет три outcome, секрет webhook, владельца и ID отправленного
  сообщения, повторные callback и прежний ответ через Mini App. Repository integration запускается
  только на отдельной локальной PostgreSQL.
- Изменение critical flow обновляет хотя бы один mobile E2E smoke.
- Режим «Без телефона» проверяет допустимый состав задания, сохранённый `completionSource`, отказ
  таймера в обычном режиме, паузу при скрытии WebView, десятисекундную подготовку, переход только
  после ответа сервера, доступность итоговой оценки и визуальный путь без speech API. Integration
  запускается только на отдельной disposable PostgreSQL, а звук вручную в Telegram iOS/Android.
- Для version 12 проверить 15 и 25 секунд наблюдения на клиенте и сервере; version 11 продолжает
  прежний интервал. При доступных русских голосах клиент предпочитает женский, при отсутствии голосов
  остаётся системный fallback. Значок паузы виден в остановленном таймере.
- Когнитивные задания проверяются на преждевременные/повторные нажатия и ошибочные ответы: прогресс
  увеличивается только от успешного действия, а backend независимо проверяет минимальную цель.
- Реакция отдельно проверяет границу: 500 мс не засчитываются, 499 мс засчитываются; медленная
  попытка не продвигает раунд.
- Калибровка проверяется на полном и двигательном профиле: первые семь сопоставимых назначений
  должны давать семь разных фактических последовательностей до начала проверочных повторов.
- Для бюджета 10 минут component/domain tests подтверждают увеличенные цели и интервалы; режимы 2/5
  минут сохраняют базовую нагрузку.
- Новое назначение содержит не более одного светового шага `window`; legacy-сессия с `curtains`
  отдельно проверяется на отображение и завершение.
- Для сохранённых protocol version 7 сценариев проверяется прежний состав; новые version 8
  назначения проверяются по временному бюджету и отсутствию запрещённых дополнений, а не по жёсткому
  числу шагов.
- Для protocol version 8 режимы 2/5/10 минут проверяются на плановый диапазон 90–110%; если профиль
  не позволяет его набрать, тест фиксирует безопасный `limited_eligible_tasks`, а не запрещённое
  дополнение.
- Для новых пятиминутных назначений version 10 полный профиль даёт 6–7 шагов и план 270–330 секунд;
  клиент и сервер требуют четыре успешных когнитивных раунда (три для памяти), длинные интервалы
  нельзя подтвердить досрочно. Сохранённые version 8/9 продолжаются со старыми целями.
- `sit_edge` проверяется как единственный переход непосредственно перед первым стоячим/физическим
  действием: когнитивное задание может оставаться первым, а переход не повторяется перед каждым
  последующим движением.
- Первичная анкета проверяет последовательность legal → возможности → home/wake, отдельные карточки
  упражнений и отсутствие неподтверждённых task IDs в назначении.
- Home Screen prompt проверяется после первого завершения: вызов Telegram API только после жеста,
  ручной fallback и отсутствие повторного показа на устройстве.
- Личная цель проверяется как необязательная локальная настройка: Enter сохраняет короткий текст,
  пропуск не блокирует сценарий, а удаление профиля очищает user-scoped запись на устройстве.
- Для новой серверной жизненной цели отдельно проверить auth, `If-Match`, idempotency, изоляцию
  пользователей и каскадное удаление на disposable PostgreSQL. Утреннее уведомление содержит
  сохранённую цель; при пустой цели текст нейтрален. Локальную цель не загружать автоматически.
- Вечерняя калибровка создаётся идемпотентно только для первых трёх завершённых сессий, не появляется
  до 18:00 и не создаёт повторное утреннее уведомление.
- Каталог version 9 проверяется отдельно: старый профиль не получает `cool_wash` и `pushups`, даже
  если серверный flag включён; новый профиль должен явно разрешить умывание и активное движение.
- Умывание нельзя подтвердить раньше 20 секунд, отжимания — раньше 25 секунд; отжимания следуют
  после `sit_edge` и разминки, а разнообразие новых назначений проверяется на серии кандидатов.
- Общая отправка task result проверяется как single-flight: повторный и запоздалый callback не
  создаёт следующий переход, а после conflict разрешена честная повторная попытка.
- Полный PostgreSQL regression режима 10 минут последовательно отправляет все десять результатов с
  канонической версией после каждого шага и завершает сессию.
- Wake engagement foundation проверяется на чистой PostgreSQL 17: вся migration chain применяется
  с нуля и повторно как no-op, sound mode сохраняется без системной громкости, substitution replay
  идемпотентен, чужая сессия недоступна, recovery shape ограничен БД, а удаление профиля каскадно
  очищает append-only историю замен.
- Интеграционный сценарий замены сначала меняет следующий шаг, восстанавливает сессию через
  bootstrap, затем меняет текущий шаг и снова проверяет `effectiveSteps` и append-only историю.
  Domain-тесты отдельно фиксируют профиль, бюджет, безопасный порядок, выполненные и уже отклонённые
  task IDs, а analytics-тесты исключают только нарушенное factor comparison.
- Recovery-сценарий завершает primary с эффектом `+1`, создаёт и повторяет идемпотентную команду,
  восстанавливает отдельный раунд через bootstrap, проверяет максимум два действия/90 секунд,
  provenance baseline и единственный follow-up на recovery. История показывает оба результата, а
  `averageDelta` и learning count остаются рассчитаны только по primary.
- Component-тест карточки слабого результата проверяет спокойный текст, точный предел времени,
  явный отказ и блокировку повторных действий во время запроса.
- Sequence analytics публикует порядок только после двух повторов в одинаковом контексте и бюджете;
  unit/contract-тесты проверяют раздельные группы, размер выборки, выключенный pilot flag и отсутствие
  sequence-гипотез в AI payload до включения.
- Mobile Chromium E2E отдельно проверяет замену текущего шага с причиной и серверной альтернативой,
  а также восстановление сохранённого recovery-раунда; основной wake-up цикл остаётся отдельным
  сквозным сценарием.
- Для звука проверить: без жеста AudioContext не создаётся; после выбора «Со звуком» сигнал
  повторяется до mute или ухода с экрана; ошибка Web Audio не прерывает задания. На реальных Telegram
  iOS/Android вручную проверить слышимость, системную громкость и возобновление после возврата в
  Mini App, не обещая звук при его закрытии или блокировке устройства.
- Мобильный viewport проверяет одинаковую вертикальную ось кнопок «Протокол» и звука, отсутствие
  растянутой карточки и доступность CTA без скролла. Для приседаний проверяются две позы, при
  reduced motion — одна статичная поза; таймер использует одно кольцо.
- Статистика всегда показывает «Следующий шаг»: при загрузке профиля без ложного 0/7, при нуле
  завершённых сессий с первым протоколом, при 1–6 с оставшимся числом до общего профиля, при 7+
  с проверяемым действием даже без вызова AI.
- E2E закрытия сохранённой сессии подтверждает возврат на главную без вызова Telegram `close()`.
- Профиль проверяется на отсутствие дублирующих KPI и технического confidence, дедупликацию factor
  progress, понятную рекомендацию и график положительных, нулевых и отрицательных session delta.
- Экран завершения проверяется с серверным evidence count 7+ и не должен обещать ложные «ещё N».
- Не закреплять внутреннюю реализацию, если пользовательский контракт можно проверить напрямую.

## PostgreSQL

Integration tests должны выполняться на disposable database. Безопасный вариант — локальный контейнер
из `compose.yaml`. Перед использованием удалённой тестовой БД проверьте имя хоста и базы вручную.
Миграции тестируются с нуля и повторным запуском. Нельзя редактировать уже выпущенные SQL-файлы ради
прохождения теста; создайте следующую migration.

## CI

`.github/workflows/ci.yml` запускается для pull request и push в `master`/`dev`:

- job `verify`: PostgreSQL 17, install, format, typecheck, migrate, unit/contract, integration,
  build, bundle/security boundaries и mobile Chromium E2E;
- job `security`: production dependency audit;
- при E2E-ошибке сохраняются Playwright report и traces;
- новый push отменяет устаревший CI того же ref.

Красный обязательный job блокирует merge. Локальный успех не заменяет CI.

## Ручной smoke-test

Автоматизация не заменяет проверку внутри Telegram:

1. новый вход и legal gate;
2. старт, закрытие Mini App и продолжение активной сессии;
3. baseline, все задания, post-rating и результат;
4. follow-up из Telegram через 15 минут;
5. расписание и snooze;
6. история, профиль после 7+ сессий, лучший порядок и progress factor pairs;
7. отсутствие AI-вызова до кнопки, AI fallback/ответ и дневной лимит;
8. отсутствие immediate repeat при доступной альтернативе и соответствие задания бюджету/анкете;
9. реакция не нажимается до сигнала, ошибки внимания/памяти не завершают шаг, а 10 минут дают
   увеличенное число раундов и интервалы;
10. одинаковый стартовый протокол в разных контекстах объяснён как калибровка, а накопленные
    результаты контекстов не смешиваются;
11. удаление тестового профиля;
12. `/admin` разрешённому и обычному пользователю, включая second-session rate и pending;
13. при billing rollout — checkout, renewal, cancel, support и refund в test environment.
14. при первом входе после документов анкета возможностей не позволяет начать сессию до сохранения;
15. когнитивное начало сохраняется, а «Сесть на край кровати» появляется только перед первым
    заданием, где требуется подъём;
16. после первого завершения Home Screen prompt работает на поддерживаемом клиенте и не блокирует
    результат на неподдерживаемом.
17. цель сохраняется с мобильной клавиатуры, показывается перед исходной оценкой, допускает пропуск и
    исчезает после удаления профиля;
18. после каждой из первых трёх сессий карточка обещает только вечернюю проверку, а после 18:00
    открывает доступные настройки без нового утреннего push.
19. при включённом пилотном флаге повторяемый порядок показывает число сопоставимых сессий и
    непричинную оговорку; единичный порядок и одинаковые шаги при другом контексте/бюджете не
    называются лучшими.
20. до трёх завершённых пробуждений статистика объясняет нехватку данных без кнопки AI-отчёта;
    сервер возвращает `unavailable` даже с прежним `confirmEarly: true` и не читает cache/provider.
    После третьего пробуждения кнопка доступна, отчёт создаётся только по нажатию, cache и дневной
    лимит продолжают действовать.

Устройства: Telegram iOS, Android и Desktop. Сейчас Android остаётся ручным пробелом; mobile Chromium
покрывает layout/flow, но не заменяет Telegram Android WebView.

Последний подтверждённый прогон ищите в актуальном handoff из
[`handoffs/CURRENT.md`](handoffs/CURRENT.md). `.specify/feature.json` указывает на завершённый
Spec Kit feature 017: его `validation.md` подтверждает только тот исторический этап, а не текущий
OpenSpec change и не production deploy.

Полный ручной прогон режимов 2/5/10 минут, контекстов, семи контрольных сессий, удаления профиля,
Telegram-сообщений и реального личного цикла описан в
[`pre-pilot-manual-test-plan.md`](pre-pilot-manual-test-plan.md).

## Публичное портфолио и отдельная тестовая БД

`pnpm test:integration` требует явно заданную локальную PostgreSQL с отдельным `test` в имени БД.
Отсутствующая, удалённая или обычная БД отклоняется до запуска тестов. Имя — дополнительный барьер,
а не доказательство безопасности: не направляйте production-туннель на localhost.

Пример полностью одноразового окружения (все значения ниже — локальные fixtures):

```bash
docker run --rm -d --name prosnix-integration-test \
  -e POSTGRES_DB=prosnix_test -e POSTGRES_USER=fixture -e POSTGRES_PASSWORD=fixture \
  -p 127.0.0.1:55438:5432 postgres:17-alpine
# Дождитесь готовности БД: docker exec prosnix-integration-test pg_isready -U fixture
cd packages/db
DATABASE_URL='postgres://fixture:fixture@127.0.0.1:55438/prosnix_test' node node_modules/drizzle-kit/bin.cjs migrate
cd ../..
DATABASE_URL='postgres://fixture:fixture@127.0.0.1:55438/prosnix_test' pnpm verify:release:full
pnpm test:demo
docker stop prosnix-integration-test
```

Для этой проверки не загружается `.env`; production БД не используется. Обычный `db:migrate`
предназначен для своей локальной разработки с явно проверенной конфигурацией.

`pnpm verify:module-size` проверяет TS/TSX/JS/MJS/CSS в apps, packages, scripts и tests.
Сгенерированные migrations и lockfile не разделяются вручную. `pnpm test:demo` проверяет отдельную
собранную demo-версию, включая отсутствие запросов к API и сторонним сервисам.

Secret scan в CI охватывает историю и чистое дерево checkout; dependency audit включает инструменты
разработки. Единственное исключение `.gitleaksignore` — точный fingerprint исторического
синтетического idempotency key. Нельзя исключать целиком tests или произвольные commits.
