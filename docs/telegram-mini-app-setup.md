# Настройка Telegram-бота и мини-приложения

Инструкция описывает локальный запуск и размещение на Render с PostgreSQL в Neon.
Для автономного демо бот, БД и ключи не нужны: выполните `pnpm dev:demo`.
Для работы с реальными данными настройте собственную тестовую среду.

## Подготовка

Нужны Node.js 22–24, pnpm 11.19.0 и Docker для локальной PostgreSQL.
Проверьте версии в терминале:

```bash
node --version
pnpm --version
```

Создайте бота через BotFather и сохраните токен. Одного бота достаточно для первой тестовой среды.
Перед рабочим выпуском отдельно проверьте разделение ботов, баз и секретов.
Токен не передаётся в Git, клиентский код или переменные `VITE_*`.
При случайной публикации замените его через BotFather.

## Локальные настройки

В корне `prosnix` создайте `.env` из [.env.example](../.env.example):

```bash
cp .env.example .env
```

Заполните собственный токен и случайные секреты. Пример подключения к локальной БД:

```dotenv
NODE_ENV=development
API_PORT=3001
POSTGRES_PORT=5432
DATABASE_URL=postgres://awc:awc@localhost:5432/awc
```

Эти учётные данные предназначены только для локальной разработки.
Для `SESSION_SECRET` и отдельно для `CRON_SECRET` сгенерируйте разные строки:

```bash
openssl rand -hex 32
```

API при разработке сам читает корневой `.env`; выполнять `source .env` не нужно.
После изменения настроек перезапустите процесс. Проверьте исключение файла из Git:

```bash
git status --ignored --short .env
```

Ожидаемый префикс — `!! .env`.

## Запуск на компьютере

```bash
pnpm install --frozen-lockfile
pnpm db:start
pnpm db:migrate
pnpm dev
```

Клиент открывается на `http://localhost:5190/`, API — на `http://localhost:3001/health`.
Если порт PostgreSQL занят, одновременно измените `POSTGRES_PORT` и порт в `DATABASE_URL`.
При занятом порте API измените `API_PORT` и согласуйте адрес клиента с настройками проекта.
Для входа из Telegram нужен HTTPS-адрес; `localhost` в BotFather для удалённого запуска не подходит.

## Где хранятся настройки

| Место                  | Назначение                                 |
| ---------------------- | ------------------------------------------ |
| Локальный `.env`       | Только свои настройки разработки           |
| BotFather              | Бот, HTTPS-адрес, кнопка и оформление      |
| Окружение API в Render | Серверные секреты и подключение к БД       |
| Neon                   | Данные приложения и параметры PostgreSQL   |
| Render Static Site     | Собранный клиент, без серверных секретов   |
| cron-job.org           | Адрес плановой отправки и отдельный секрет |

Раздел переменных хостинга может называться `Environment`, `Variables` или `Secrets`.
Названия в интерфейсе сервиса оставлены здесь на английском, чтобы их было проще найти.
Локальный `.env` не переносится на хостинг автоматически.

## База данных Neon

1. Создайте проект в [панели Neon](https://console.neon.tech/).
2. Выберите регион с учётом расположения API.
3. Через `Connect` получите строку PostgreSQL с шифрованным подключением.
4. Для миграций используйте совместимый способ прямого подключения;
   не подменяйте его подключением через пул без проверки.
5. Добавьте строку только в окружение API как `DATABASE_URL`.
6. Проверьте резервное копирование и доступный тарифу период восстановления.

Строку подключения нельзя помещать в BotFather, Git или клиент React.
Рабочая БД не используется для интеграционных тестов.

## API в Render

В [панели Render](https://dashboard.render.com/) выберите `New` → `Web Service`
и подключите репозиторий. Укажите нужную ветку; `Root Directory` оставьте пустым,
так как сборка использует общий репозиторий.

Команда сборки в `Build Command`:

```bash
corepack enable && pnpm install --frozen-lockfile && pnpm db:migrate && pnpm build
```

Эта команда применяет миграции к настроенной БД. Для рабочей среды нужны отдельное разрешение
и проверка резервной копии. Команда запуска в `Start Command`:

```bash
pnpm start:api
```

В `Health Check Path` укажите `/ready`. Путь `/health` проверяет только процесс,
а `/ready` — также доступность PostgreSQL.

В `Environment` добавьте серверные переменные по `.env.example`:

| Переменная                      | Значение                                          |
| ------------------------------- | ------------------------------------------------- |
| `DATABASE_URL`                  | Строка подключения к выбранной PostgreSQL         |
| `TELEGRAM_BOT_TOKEN`            | Токен собственного бота                           |
| `SESSION_SECRET`                | Отдельная случайная строка                        |
| `TELEGRAM_WEB_APP_URL`          | HTTPS-адрес статического сайта                    |
| `TELEGRAM_AUTH_MAX_AGE_SECONDS` | Допустимый возраст данных запуска, например `900` |
| `CRON_SECRET`                   | Другая случайная строка для планировщика          |
| `DEEPSEEK_API_KEY`              | Необязательный ключ отчётов DeepSeek              |
| `DEEPSEEK_BASE_URL`             | Адрес API провайдера из конфигурации              |
| `DEEPSEEK_MODEL`                | Поддерживаемая модель из настроек проекта         |
| `DEEPSEEK_TIMEOUT_MS`           | Время ожидания ответа модели                      |

Остальные ограничения и параметры готовности также описаны в `.env.example`.
Render задаёт `PORT`; API умеет его читать. Серверные секреты не добавляются статическому сайту.
После сборки проверьте `/health` и `/ready`. Холодный запуск сервера после простоя
может задерживать первый запрос; доступность нужно измерить перед рабочим выпуском.

## Статический сайт в Render

Создайте `New` → `Static Site` из того же репозитория и совместимого коммита.
`Root Directory` оставьте пустым. В `Build Command` укажите:

```bash
corepack enable && pnpm install --frozen-lockfile && pnpm --filter @awc/web build
```

Предварительная сборка пакета сама собирает `@awc/domain`. Прямой `vite build`
на чистом рабочем каталоге может не найти его готовые файлы.
В `Publish Directory` укажите `apps/web/dist`.

В `Redirects/Rewrites` добавьте правила в таком порядке. Вместо `API_HOST` подставьте
фактический HTTPS-хост API:

| Исходный путь | Назначение                | Действие  |
| ------------- | ------------------------- | --------- |
| `/api/*`      | `https://API_HOST/api/*`  | `Rewrite` |
| `/health`     | `https://API_HOST/health` | `Rewrite` |
| `/ready`      | `https://API_HOST/ready`  | `Rewrite` |
| `/*`          | `/index.html`             | `Rewrite` |

Первые правила позволяют клиенту и API работать через один публичный адрес.
Последнее обслуживает маршруты React. Проверьте ответы `/health` и `/ready` через адрес сайта,
а затем сохранение защищённой cookie при входе из Telegram.
Не ослабляйте защиту cookie ради обхода ошибки перенаправления.

## Плановая отправка через cron-job.org

Одна задача раз в пять минут обслуживает напоминания и повторную проверку после протокола.
БД и токен бота остаются в API; планировщик получает только отдельный `CRON_SECRET`.

В [панели cron-job.org](https://console.cron-job.org/) создайте задачу:

| Поле            | Значение                                           |
| --------------- | -------------------------------------------------- |
| URL             | `https://API_HOST/internal/notifications/dispatch` |
| Расписание      | Каждые пять минут: `*/5 * * * *`                   |
| Метод           | `POST`                                             |
| Заголовок       | `Authorization: Bearer ВАШ_CRON_SECRET`            |
| Тип содержимого | `Content-Type: application/json`                   |
| Тело            | `{}`                                               |
| Время ожидания  | 30 секунд                                          |

Замените `API_HOST` адресом API. В Render хранится сама секретная строка;
в заголовке планировщика перед ней стоит `Bearer ` с пробелом.
Дополнительная HTTP-аутентификация по имени и паролю не используется.
Не передавайте планировщику `DATABASE_URL`, `SESSION_SECRET` или токен Telegram.

Сначала оставьте задачу выключенной и выполните тестовый запуск:

- `200` — запрос обработан; при отсутствии ожидающих сообщений счётчики могут быть нулевыми.
- `401` — не совпадает секрет.
- `415` — неверный тип содержимого или отсутствует тело `{}`.
- `409` — предыдущая отправка ещё выполняется.
- `503` — не хватает необходимой серверной конфигурации.

После успешной проверки включите расписание. Настройте уведомления о последовательных сбоях.
API также удаляет технические журналы доставки старше 90 дней; сессии и оценки сохраняются.

## Настройки BotFather

После успешной проверки API:

1. Отправьте `/mybots` и выберите бота.
2. Через `Bot Settings` → `Configure Mini App` включите мини-приложение и укажите HTTPS-адрес сайта.
3. Настройте название, изображение и экран загрузки.
4. Через `Menu Button` или `/setmenubutton` добавьте кнопку «Открыть Prosnix» с тем же адресом.
5. В настройке политики конфиденциальности укажите адрес страницы `/privacy` этого сайта.

Команда `/setprivacy` управляет получением групповых сообщений, а не политикой мини-приложения.
Проверьте реальные реквизиты оператора данных на правовых страницах до запуска для пользователей.

Основное мини-приложение открывается ссылкой `https://t.me/<BOT_USERNAME>?startapp`.
Один процесс API проверяет подпись только токеном настроенного бота. Переключение бота требует
согласованного изменения токена; добавление второго имени в BotFather этого не заменяет.

Напоминания не требуют входящих событий бота. Для ответов на повторную проверку прямо в чате
нужны отдельно настроенные `TELEGRAM_WEBHOOK_SECRET` и обработчик `/internal/telegram/webhook`.
Изменение регистрации обработчика и секретов выполняется только с разрешения владельца.

## Проверка Telegram и DeepSeek

На iOS, Android и компьютере проверьте вход, исходную оценку, задание,
продолжение после закрытия, завершение, историю и повторную проверку.
Используйте отдельный тестовый профиль и проверьте его удаление.

`telegram_auth_failed` может означать запуск вне Telegram, неверный токен,
смешение тестовой и рабочей среды, расхождение часов или устаревший `initData`.
Не публикуйте эти данные для диагностики.

Отчёт DeepSeek запрашивается явно, начиная с трёх завершённых сессий.
Ключ хранится только в API. Модель получает агрегаты, без Telegram ID, UUID сессий,
точного времени и исходных ответов. Без ключа или при ошибке доступен базовый отчёт.
Продажи оставьте выключенными через `TELEGRAM_STARS_MONTHLY_PRICE=0`, пока не пройдены
отдельные [проверки выпуска](release-checklist.md).

## Проверки перед запуском

- [ ] `.env` исключён из Git; секреты доступны только API.
- [ ] БД не опубликована для прямого доступа клиентов; миграции применены.
- [ ] Клиент и API доступны через один HTTPS-адрес.
- [ ] `/health` возвращает `{"status":"ok"}`, `/ready` — `{"status":"ready"}`.
- [ ] Бот и кнопка запуска настроены; реальные сценарии проверены на устройствах.
- [ ] Резервная копия и восстановление проверены.
- [ ] Правовые страницы содержат фактические сведения об операторе.
- [ ] Публикуемый SHA и разрешение на рабочий выпуск зафиксированы отдельно.
