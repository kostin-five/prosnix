# Архитектура Prosnix

Prosnix — модульный монолит в общем рабочем пространстве pnpm. Клиент, API и библиотеки
собираются отдельно; доменные правила и хранение данных остаются в одном репозитории.
Планы развития описаны в [дорожной карте](product-roadmap.md).

## Общая схема

```text
Клиент Telegram
  → Статический сайт Render: React/Vite
  → Перенаправление /api на том же адресе
  → Сервер Render: Fastify API
       → PostgreSQL в Neon
       → Telegram Bot API
       → DeepSeek API, если настроен

Планировщик cron-job.org
  → POST /internal/notifications/dispatch
  → API → резервирование отправки в PostgreSQL → Telegram Bot API
```

## Клиент

`apps/web` использует React 18 и Vite 6. Он отвечает за вход через Telegram,
первичную анкету, выбор контекста и длительности пробуждения, задания, оценки,
историю, статистику и настройки. Правовые страницы `/privacy` и `/terms` доступны без входа.
Административная панель `/admin` загружается отдельно и доступна только разрешённым пользователям.

Первичная загрузка ограничена двадцатью секундами. При задержке серверного запуска
появляется сообщение с повторной попыткой. Настройки, задания, статистика, правовые страницы
и административная панель загружаются отдельными частями сборки. Ошибка загрузки не удаляет
сохранённый ход сессии. `verify:web-bundle` ограничивает начальный JavaScript размером 240 КиБ.

До первого принятия документов правовые ссылки открываются в том же окне мини-приложения,
чтобы сохранить данные запуска Telegram. Анимации учитывают `prefers-reduced-motion`.
Звук запускается после действия пользователя и работает только при открытом приложении.

## Сервер и домен

`apps/api` использует Fastify 5. `createApp` собирает зависимости, а `server.ts`
подключает репозитории и внешние сервисы для рабочего запуска.

| Модуль            | Ответственность                                                       |
| ----------------- | --------------------------------------------------------------------- |
| `auth`            | Проверка подписи Telegram, срока данных запуска и серверной сессии    |
| `sessions`        | Переходы сессий, версии, защита повторяемых операций                  |
| `personalization` | Возможности пользователя, личный распорядок и его выполнение          |
| `analytics`       | Пересчёт статистики из исходных наблюдений                            |
| `coach`           | Обезличенный контекст, DeepSeek, проверка ответа, кэш и базовый отчёт |
| `notifications`   | Расписание, отложенные напоминания, отправка и повторные попытки      |
| `legal`           | Версии документов и их принятие                                       |
| `billing`         | Основа оплаты Telegram Stars; продажи по умолчанию выключены          |
| `admin`           | Сводные показатели продукта и эксплуатации                            |
| `observability`   | Структурированные события и идентификаторы запросов                   |
| `runtime`         | Проверка готовности и корректное завершение процесса                  |

`packages/domain` содержит модели, переходы состояний, подбор протокола, аналитику,
расписание и интерфейсы репозиториев. Он не зависит от React, Fastify, Drizzle и внешних API.
`packages/contracts` задаёт схемы обмена. Типы клиента не заменяют серверную проверку
пользователя, принадлежности данных, состояния и условий оплаты.

Карта маршрутов приведена в [API-контрактах](api-contracts.md).

## Вход и доступ

1. Telegram передаёт подписанный `initData`.
2. Клиент отправляет его в `POST /api/v1/auth/telegram`.
3. API проверяет HMAC токеном бота и допустимый возраст данных.
4. Пользователь создаётся или находится по Telegram ID.
5. API устанавливает подписанный файл cookie `awc_session` с `HttpOnly` на 30 дней.
6. Персональные маршруты получают внутренний UUID пользователя только из серверной сессии.

Cookie имеет `SameSite=Strict`, а в рабочей среде — также `Secure`.
Административные маршруты дополнительно проверяют `ADMIN_TELEGRAM_USER_IDS` и возвращают
`404` пользователям без разрешения.

## Сессия пробуждения

```text
assigned → in_progress → protocol_completed → наблюдение через 15 минут
                  ↘ abandoned
```

Записи используют `Idempotency-Key`; переходы требуют актуальную версию в `If-Match`.
Ограничения PostgreSQL не допускают две активные сессии одного пользователя,
повторную оценку одного типа или повторный результат шага. Начальная загрузка возвращает
активную сессию и ожидающую повторную проверку, поэтому после закрытия можно продолжить
с подтверждённого шага.

Пользователь выбирает контекст сна и длительность 2, 5 или 10 минут. Сервер применяет
профиль возможностей и сохраняет неизменяемый снимок ограничений. Если разрешённых заданий
недостаточно, назначается короткий допустимый вариант. Расписание для ручного запуска не требуется.

В обычном режиме клиент ждёт подтверждения сервера перед следующим шагом.
В режиме без телефона используются только задания без экранного ответа и источник завершения
`timer`. Сервер проверяет режим, результат и минимальную длительность по своим часам.
Таймер не доказывает физическое выполнение упражнения.

Когнитивные задания требуют успешных раундов: ошибка остаётся попыткой и не продвигает шаг.
Нажатие в задании на реакцию засчитывается только быстрее 500 мс: 499 мс подходит, 500 мс — нет.
Сервер независимо проверяет минимальные цели. Сохранённые версии протоколов продолжаются
с назначенными им правилами и интервалами.

Перед первым заданием стоя или с физической нагрузкой добавляется переход `sit_edge`.
Интенсивной нагрузке предшествует разминка. Отжимания требуют полного уровня движения,
разрешений `active_movement`, `floor_space` и отсутствия исключения. Умывание требует `wash_access`.
Новые обычные назначения версии 15 используют `learning-v8` и `adaptive-v8`;
режим без телефона — `hands-free-adaptive-v2`. Подробности — в [описании подбора](protocol-selection.md).

Новый световой шаг имеет идентификатор `window` и название «Яркий свет».
Старый `curtains` поддерживается для ранее назначенных сессий. Инструкция предлагает дневной свет
или комнатное освещение, но не взгляд прямо на солнце. Дыхание имеет идентификатор `breathing`
и длится 30 секунд. Пользователь может исключить его в настройках возможностей.

## Замена, досрочное завершение и дополнительный раунд

Замена включена по умолчанию; согласованные настройки сервера и клиента со значением `false`
позволяют её отключить. Сервер учитывает профиль, оставшееся время, безопасный порядок,
выполненные и уже отклонённые задания. Исходное назначение не меняется; новые события
формируют `effectiveSteps` без перезаписи предыдущих замен. Причина `cannot_do` предлагает
отдельно подтвердить изменение будущего профиля.

Кнопка «Проснулся» открывает итоговую оценку. После её сохранения остаются реальные результаты
выполненных шагов и отметка `completedEarly`. Невыполненные задания не получают вымышленных
результатов. Сессия видна в истории и получает повторную проверку, но исключается из обучения
и аналитики полных протоколов. Дополнительный раунд ей не предлагается.

После полного основного протокола с изменением не выше `+1` сервер может предложить
необязательный дополнительный раунд. Основной результат уже сохранён. Раунд содержит не более
двух других допустимых действий суммарно до 90 секунд; его исходная оценка берётся из итоговой
оценки основной сессии. Принятие переносит единственную повторную проверку на последний
завершённый этап. Явный отказ сохраняется. Основная статистика учитывает только
`session_kind=primary`.

Таймеры упражнений запускаются при видимом открытии без дополнительной кнопки «Начать».
Между шагами можно выбрать паузу 5, 10 или 20 секунд либо идти без паузы. Настройка относится
к пользователю и устройству. До выбора обычный режим идёт без паузы, режим без телефона —
с паузой 10 секунд. Пауза и скрытие окна останавливают отсчёт. Голос зависит от устройства;
при наличии подходящих русских системных голосов выбирается женский.

## Наблюдения и аналитика

Назначение хранит версии протокола, стратегии и метода, фазу, гипотезу и снимок наблюдений.
Исходные оценки, результаты и ответ через 15 минут не перезаписываются отчётом ИИ.
Профиль пересчитывается из сохранённых наблюдений.

Основная метрика — разница итоговой и исходной оценок завершённой основной сессии.
Досрочные и дополнительные сессии не смешиваются с полными основными протоколами.
Сравнения разделены по контексту сна и времени. Общий эффект смешанного протокола
не приписывается каждому упражнению.

После семи полных сессий доступен общий профиль. `analytics-v2` публикует результат точного
порядка только после двух повторов в одинаковых условиях, с размером выборки `n`
и оговоркой об отсутствии доказанной причинности. Для факторов возвращаются числа наблюдений
с фактором и без него, число сопоставимых пар и цель в три пары. Недостаток пар не скрывает
общий профиль. Гипотезы о порядке передаются клиенту и ИИ только при
`WAKE_COMBINATION_ANALYTICS_ENABLED=true`; по умолчанию настройка выключена.

Дневная динамика — среднее парное изменение по локальным датам. Разные контексты объединяются
только в этом обзорном ряду. Личный распорядок и жизненная цель не участвуют в обучении.
Цель хранится в `user_life_goals` только после явного сохранения; локальный текст не загружается
на сервер автоматически. Она доступна владельцу, добавляется в личное напоминание
и удаляется каскадно с профилем.

После пяти завершений один раз предлагается обратная связь о полезности, раздражении
и намерении продолжать. После семи может появиться исследование интереса к будущему Pro.
Эти ответы не меняют назначение, оценки и доступ к приложению.

## Отчёт DeepSeek

Запрос выполняется только сервером и только по нажатию пользователя, начиная с третьей
завершённой сессии. До этого возвращается `unavailable` без чтения кэша и вызова модели.
Внешний запрос содержит агрегаты и производные сигналы динамики, без Telegram ID, UUID,
точного времени, идентификаторов наблюдений, cookie и исходных ответов.

Сервер допускает один новый внешний отчёт за локальный день, проверяет его структуру
и кэширует по отпечатку входных данных. При отсутствии ключа или сбое возвращается
детерминированный базовый отчёт. Открытие статистики не вызывает модель.
Неудачный сохранённый базовый отчёт допускает новую попытку после локальной полуночи.
Успешный отчёт при неизменных агрегатах сохраняется. Новые данные в тот же день отражаются
детерминированным расчётом без второго обращения к модели.

Событие `coach_provider_failed` содержит безопасную причину и HTTP-статус при наличии.
Исходная ошибка, тело ответа и данные пользователя не журналируются.

## Уведомления и платежи

cron-job.org раз в пять минут отправляет защищённый запрос в API.
Сервер резервирует ожидающие доставки в PostgreSQL, делает ограниченные повторные попытки
и удаляет технические журналы старше 90 дней. Параллельная отправка в одном процессе получает `409`.

Защищённый обработчик Telegram позволяет ответить на повторную проверку прямо в чате.
Проверяются пользователь, личный чат и запись конкретной доставки. Первое наблюдение сохраняется,
повторное нажатие его не меняет. Без обработчика сообщение ведёт в мини-приложение.

Продажи Telegram Stars выключены при `TELEGRAM_STARS_MONTHLY_PRICE=0`.
Счёт создаётся сервером после принятия актуальных документов. Обработчик проверяет отдельный
секрет до чтения события. Счета, платёжные записи, идентификаторы событий и состояние подписки
хранятся раздельно. Повторное событие не продлевает доступ дважды.
Включение продаж требует отдельного разрешения и [проверок выпуска](release-checklist.md).

## Данные и организация модулей

PostgreSQL — источник достоверных данных о пользователях, сессиях, назначениях, оценках,
уведомлениях, аналитике и платежах. `packages/db/migrations` содержит миграции только вперёд.
Удаление профиля каскадно удаляет персональные записи. Ранее применённые миграции не редактируются.

`0009_subscription_status_repair` добавляет `past_due` в старую схему.
`0010_wake_engagement_foundation` добавляет снимок условий, историю замен и ограничения
дополнительных раундов. `0011_low_effect_recovery` сохраняет явный отказ от такого раунда.
Цепочка проверяется на отдельной тестовой БД; это не подтверждение применения в рабочей среде.

`App.tsx` отвечает за начальную загрузку, принятие документов и восстановление.
`wake-app.tsx` управляет сценарием, `tasks-container.tsx` — экраном протокола,
`cognitive-tasks.tsx` — заданиями, `results-screen.tsx` — итогом, `bottom-nav.tsx` — навигацией.
`session-model.tsx` содержит типы и адаптеры; `demo-planning.ts` — вымышленные данные демо.
В БД `session-reader.ts` читает состояние, а `sessions.ts` выполняет команды в транзакции
с рекомендательной блокировкой PostgreSQL и защитой повторяемых операций.

## Среды и эксплуатация

Локально используются Docker PostgreSQL, клиент на порту `5190` и API на `3001`.
Удалённая схема — Render Static Site, Render API, Neon и cron-job.org.
`dev` — интеграционная ветка, `master` — стабильная. Проверка `/health` подтверждает работу
процесса, `/ready` — также подключение к БД. Серверные секреты находятся только в окружении API;
статический сайт получает лишь публичные `VITE_LEGAL_*`.

Откат кода не откатывает схему. Бесплатный сервер может запускаться с задержкой после простоя.
Разделение тестовых и рабочих ресурсов проверяется отдельно перед выпуском.
Журналы содержат разрешённые технические поля, но не параметры запросов и персональные ответы.
Административная панель возвращает только агрегаты; доступ к БД есть у серверных репозиториев
и средства миграций. ИИ не управляет состоянием, доступом и платежами.

## Автономное демо

Vite в режиме `portfolio` создаёт `dist-demo` без файлов окружения и Telegram SDK.
Контекст запуска всегда демонстрационный; `apiFetch` запрещает обращения к API.
Обычная рабочая сборка требует вход через Telegram. Результаты демо не являются наблюдениями
реальных пользователей и не заменяют серверный подбор.
