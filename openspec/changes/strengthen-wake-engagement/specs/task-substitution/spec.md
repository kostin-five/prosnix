# Spec Delta

## Purpose

Даёт пользователю безопасный способ заменить неподходящее утреннее задание, сохраняя исходное
назначение, причину изменения и воспроизводимость фактически выполненного протокола.

## ADDED Requirements

### Requirement: Замена текущего задания

Система SHALL позволять запросить замену для текущего незавершённого шага или непосредственно
следующего шага до его начала. Сервер MUST выбрать альтернативу из разрешённых профилем заданий,
соответствующую оставшемуся бюджету времени, и MUST NOT повторно предлагать уже отклонённое или
выполненное в этой сессии задание.

#### Scenario: Доступна безопасная альтернатива

- **WHEN** пользователь запрашивает замену текущего задания и указывает причину
- **THEN** сервер атомарно фиксирует замену и возвращает новую эффективную последовательность с альтернативным заданием

#### Scenario: Альтернатив не осталось

- **WHEN** ни одно новое разрешённое задание не помещается в оставшийся бюджет
- **THEN** система объясняет отсутствие замены и позволяет вернуться к текущему заданию либо явно завершить сессию без ложного результата

#### Scenario: Заранее заменяется следующий шаг

- **WHEN** пользователь во время текущего задания запрашивает замену непосредственно следующего шага
- **THEN** сервер сохраняет замену будущего индекса, не меняет текущий шаг и возвращает обновлённый предварительный показ

### Requirement: Причина замены

Система SHALL требовать одну из причин `unwilling_now`, `not_helpful` или `cannot_do`. Причина
`cannot_do` SHALL предлагать отдельно обновить будущие ограничения, но система MUST NOT постоянно
исключать задание без явного подтверждения пользователя.

#### Scenario: Пользователь не хочет выполнять задание сейчас

- **WHEN** выбрана причина `unwilling_now`
- **THEN** причина влияет только на текущую сессию и не исключает задание из будущих назначений

#### Scenario: Пользователь не может выполнить задание

- **WHEN** выбрана причина `cannot_do`
- **THEN** система предлагает сохранить ограничение профиля отдельным подтверждаемым действием

#### Scenario: Пользователь считает задание бесполезным

- **WHEN** выбрана причина `not_helpful`
- **THEN** система сохраняет субъективный сигнал отдельно от измеренного эффекта и не объявляет задание неэффективным по одной замене

### Requirement: Надёжность и воспроизводимость замены

Команда замены SHALL требовать `Idempotency-Key` и актуальный `If-Match`. Система MUST сохранять
исходное назначение, каждую подтверждённую замену и фактически выполненную последовательность.

#### Scenario: Повтор команды после потери сети

- **WHEN** клиент повторяет команду с тем же `Idempotency-Key`
- **THEN** сервер возвращает тот же результат и не создаёт вторую замену

#### Scenario: Возобновление Mini App

- **WHEN** пользователь повторно открывает приложение после подтверждённой замены
- **THEN** bootstrap возвращает актуальное альтернативное задание и историю замен текущей сессии

### Requirement: Честная аналитика после замены

Система SHALL строить пользовательскую историю по фактически выполненным заданиям. Если замена
нарушила запланированное факторное сравнение, система MUST исключить эту сессию из соответствующего
сравнения, сохранив её для общего парного результата.

#### Scenario: Замена сохраняет сравниваемый фактор

- **WHEN** альтернативное задание не меняет фактор текущего сравнения
- **THEN** сессия остаётся допустимой для сравнения и содержит фактическую последовательность

#### Scenario: Замена меняет сравниваемый фактор

- **WHEN** альтернативное задание изменяет наличие исследуемого фактора
- **THEN** сессия не используется в этом факторном сравнении и интерфейс не приписывает результат исходному варианту
