# Design

## Context

См. [proposal.md](proposal.md). Prosnix остаётся «Лабораторией пробуждения»: сервер назначает
воспроизводимые протоколы, хранит исходные наблюдения и постепенно подбирает пользователю действия,
порядок и сочетания. Безопасная последовательность категорий задаёт только границы планировщика, а
не один универсальный рецепт.

Сейчас запуск из утреннего Telegram-уведомления открывает промежуточный экран будильника. Переход с
него к исходной оценке не создаёт серверную сессию, поэтому сценарий может выглядеть начатым, но не
иметь канонического состояния. После принятия документов новый пользователь также может попасть в
основной интерфейс до явной настройки физических возможностей и доступных ресурсов.

Назначение ограничивает только максимальную длительность, поэтому выбранные пять минут иногда дают
двухминутный протокол. Экран задания постоянно показывает объяснение протокола, но не даёт заранее
увидеть следующий шаг. Telegram WebView может блокировать autoplay и не на всех клиентах
поддерживает добавление Mini App на главный экран; оба улучшения должны иметь безопасный fallback.

Primary outcome — парная разница baseline и post-rating завершённой основной сессии. Продолжение
после post-rating хранится отдельно. Новые утверждения о пользе не добавляются: сочетания считаются
личными рабочими гипотезами только после повторов в сопоставимых условиях.

## Goals / Non-Goals

**Goals:**

- открыть утренний сценарий сразу на исходной оценке и всегда создать либо восстановить серверную
  сессию;
- провести нового пользователя после документов через отдельные страницы настройки возможностей:
  уровень движения, исключение упражнений, доступные ресурсы и длительность, без горизонтального
  скролла и Пикса;
- приблизить плановую длительность к выбранной — целевой диапазон 90–110%;
- сохранить индивидуальный подбор и сравнивать не только задания, но и порядок/сочетания;
- показать следующий шаг заранее и позднее разрешить заменить текущий либо следующий шаг с причиной;
- снизить утреннюю нагрузку помещающимся на экран shell, предложением ярлыка после первого
  завершения, жизненной целью в wake-сообщении и перед протоколом и минимальным действием «сесть на
  край кровати»;
- добавить звук, доступные анимации, два обоснованных кандидата заданий и отдельный recovery-сценарий.

**Non-Goals:**

- заменять системный будильник, слать повторное утреннее уведомление или обещать гарантированное
  пробуждение;
- фиксировать для всех цепочку «минимальное действие → среда → движение → концентрация»;
- использовать фоновый звук, микрофон, камеру или датчики движения;
- вводить третье новое упражнение до данных пилота;
- автоматически запрещать задание после одного субъективного ответа;
- смешивать recovery с основной экспериментальной метрикой;
- проводить полный редизайн шрифтов в первых двух технических этапах.

## Decisions

### 1. Выпускать изменение независимыми вертикальными этапами

1. Исправить прямой вход из уведомления и упростить информационную архитектуру задания/статистики.
2. Добавить обязательную первую настройку, стартовое действие, честный бюджет времени и предложение
   ярлыка после первого завершения.
3. Добавить личную цель, вечернюю калибровку первых трёх сессий и новый визуальный shell.
4. Включить звук и доступные анимации.
5. Добавить versioned-каталог из умывания и отжиманий.
6. Добавить замену текущего или следующего шага с причиной.
7. Добавить отдельный recovery при эффекте не выше +1 и анализ сочетаний.

Каждый этап проверяется отдельно. Feature flags требуются для экспериментальных этапов 3–7;
исправление сломанного входа и удаление лишнего текста не скрываются за флагом.

### 2. Утренний deep link создаёт каноническую сессию до ввода оценки

`?source=wake` сразу открывает baseline rating. Клиент один раз вызывает существующее создание
сессии с контекстом `night_sleep` и сохранённой длительностью профиля. Если сервер возвращает
конфликт, UI восстанавливает каноническую активную сессию. Отправка оценки заблокирована, пока
создание/восстановление не подтверждено; при ошибке доступен явный повтор.

Промежуточный экран будильника из Mini App удаляется. Планировщик уведомлений и системный Telegram-
баннер остаются точкой входа; ручной запуск с главного экрана продолжает спрашивать контекст.

### 3. После документов обязательна первая настройка возможностей

Порядок первого входа: юридическое согласие → последовательные страницы возможностей → главный
экран. Страница 1 спрашивает «можешь выполнять упражнения?» и выбирает уровень движения. Страница 2
показывает только соответствующие отдельные карточки движений и позволяет исключить каждое;
при уровне «без упражнений» она кратко объясняет выбор и не предлагает лишние карточки. Страница 3
спрашивает про воду, яркий свет, свободное место и, при включённом каталоге, умывание. Страница 4
задаёт обычную длительность. Кнопки «Назад» и «Далее» сохраняют локальный черновик; только
финальное действие записывает профиль на сервер. Каждая страница помещается по ширине Telegram
WebView без горизонтального скролла и не показывает Пикса. Переходы плавные и уважают reduced motion.

Ответы сохраняются в существующий профиль возможностей. Ни одно физическое или средовое задание не
назначается без явного разрешения. Редактирование той же анкеты остаётся в настройках.

### 4. «Сесть на край кровати» — переход перед движением, но не обязательный первый шаг

В protocol v8 добавляется `sit_edge`: короткое 10-секундное действие без требования стоять. Оно не
закрепляется первым: протокол может начинаться с математики, памяти, внимания или реакции. Если в
последовательности появляется первое задание, требующее встать или перейти к физической активности,
`sit_edge` вставляется непосредственно перед ним, если пользователь ещё не проходил эквивалентный
переход. Планировщик продолжает варьировать допустимые задания и порядок с учётом профиля,
исключений, истории, контекста и длительности. Ограничения безопасности не превращаются в одну
неизменяемую лестницу.

### 5. Планировщик соблюдает нижнюю и верхнюю границу времени

Для выбранной длительности целевой planned budget равен 90–110%: для пяти минут это 270–330 секунд.
Планировщик добавляет допустимые неповторяющиеся задания до нижней границы и не выходит за верхнюю.
Если профиль пользователя физически не позволяет набрать минимум, сервер возвращает максимально
близкий безопасный вариант и фиксирует причину fallback для агрегированной диагностики.

Для новых пятиминутных назначений применяется отдельная versioned политика с 6–7 шагами вместе с
`sit_edge`, если он нужен. Детерминированный планировщик распределяет недостающие секунды между
допустимыми действиями за счёт безопасного увеличения их интервалов или числа раундов, сохраняя
разнообразие состава и порядка. Плановое время должно соответствовать UI-таймерам и целям, а
серверная проверка результата — выбранной версии. Активные старые сессии продолжаются по прежним
порогам и сохранённой версии протокола. Для сильно ограниченного профиля безопасный fallback важнее
числа шагов и нижней границы времени.

Это плановая, а не фактическая длительность: пользователь может выполнить когнитивное задание
быстрее. UI показывает общий прогресс и ожидаемое оставшееся время, не обещая точный таймер.

Новая версия тайминга согласует плановый бюджет с реально показанными таймерами бытовых и
двигательных действий. Вода, шторы и включение света занимают короткий шаг; свет остаётся включённым
после перехода. Новые назначения используют новую версию, а сохранённые назначения продолжаются со
старыми интервалами и серверной проверкой. Подпись остатка суммирует задания по сохранённой версии и
округляет время без обещания точного завершения когнитивных раундов.

### 6. Shell задания показывает текущий и следующий шаг, а протокол — по запросу

Постоянный текст «Почему этот протокол» удаляется. Вверху находятся компактные действия
«Протокол» и, только после появления работающего API, «Заменить». Кнопка «Протокол» открывает sheet
с назначенной последовательностью. Под текущим заданием виден следующий шаг; до начала его можно
заменить тем же versioned API и с теми же причинами, не прерывая текущий таймер.

Кнопки «Протокол» и звука находятся в одной строке; замена доступна рядом с текущим заданием и в
предпросмотре следующего, когда серверная функция включена. На API и web функция включена по
умолчанию согласно уточнению владельца 2026-10-04; явные false overrides должны совпадать. Лишняя высота карточки не заполняется
растяжением контента: карточка следует за содержимым и оставляет свободное место ниже.
Основная кнопка действия и подтверждения текущего задания остаётся видимой в обычном viewport
Telegram iPhone без вертикального скролла: убираются жёсткие минимальные высоты, дублирующие шапки
и пустые области. На маленькой высоте или крупном системном шрифте доступен прокручиваемый fallback,
чтобы не обрезать содержание. Строка «Следующий шаг» оформляется как информация без стрелки и
кнопочного вида: она не обходит серверный переход. Для уже реализованной замены web и server flags
могут отключаться только совместно; выпуск требует CI и ручного mobile smoke.

Раздел «Справка об аналитике» удаляется из пользовательской статистики. Методологические оговорки
остаются рядом с конкретными выводами, размером выборки и сравнением.
Карточка «Следующий шаг» остаётся видимой на статистике до и после семи завершённых пробуждений:
до первой сессии предлагает пройти её, во время калибровки объясняет ближайшее повторение и
оставшееся число до общего профиля, после калибровки опирается на проверяемый порядок или
нейтральное детерминированное предложение. При загрузке серверной аналитики показывает нейтральное
ожидание, а не временный счётчик 0/7. AI может уточнить текст, но не определяет видимость карточки.
Отдельный AI-отчёт доступен с третьего завершённого пробуждения по явному нажатию. До этого
показывается прогресс до 3 и не вызывается provider. Сервер проверяет актуальный evidence count до
чтения cache, поэтому старый клиент с `confirmEarly=true` или прежний ранний cache не обходят порог.
Поле `confirmEarly` временно принимается для обратной совместимости и не даёт привилегий.
Описание персонального отчёта удаляется из настроек; сам отчёт в статистике не меняется.

### 7. Ярлык предлагается один раз после первого завершения

После первой подтверждённой основной сессии показывается спокойная карточка «Добавить Prosnix на
главный экран». На поддерживаемом Telegram-клиенте она вызывает официальный Home Screen API только
после нажатия. На неподдерживаемом клиенте показывается короткая ручная инструкция. Отказ хранится
локально на устройстве и не блокирует приложение; повторного навязчивого показа нет.

### 8. Жизненная цель помогает начать день и не становится аналитическим текстом

Пользователь может записать необязательную короткую жизненную цель, не ограниченную самим
пробуждением. Настройка прямо сообщает, что текст сохраняется на сервере и появится в личном
Telegram-чате при утреннем напоминании; текст также показывается перед началом протокола. Отдельная
user-scoped запись с forward-only migration позволяет читать его при dispatch без доступа браузера к
БД и каскадно удалять вместе с профилем. API принимает только короткий нормализованный текст от
владельца через versioned/idempotent запись. Существующую локальную цель нельзя автоматически
отправлять на сервер: пользователь должен подтвердить сохранение после нового объяснения. Пока он
этого не сделал, бот использует нейтральное сообщение. Цель не входит в audit/admin/AI, request
logs или delivery logs. После каждой из первых трёх завершённых сессий вечером предлагается
проверить настройки, без утреннего повторного push.

### 9. Звук и анимации остаются необязательными

Выбранный пользователем режим «Со звуком» запускает повторяющийся негромкий сигнал при входе в
активный протокол и останавливает его при завершении, уходе с экрана или отключении звука. Звук
разблокируется только пользовательским жестом, по умолчанию выключен на новом устройстве и имеет
no-op fallback. После закрытия Mini App или блокировки устройства непрерывность не гарантируется.
Анимации — небольшие lazy-loaded CSS-инструкции с различимыми позами и фазами
движения для приседаний и других физических действий, а не пульсация статичной иконки. Таймер
показывает одно кольцо и число без внутреннего декоративного круга. При `prefers-reduced-motion`
остаётся понятная статичная поза.
Для всех некогнитивных заданий локальные WebP-изображения показывают две последовательные фазы.
Их суммарный размер около 1,1 МБ; они загружаются с ленивым модулем задания. У шага `sit_edge`
обе фазы остаются сидячими, потому что вставание возможно лишь после 10 секунд. Текст инструкции
остаётся доступным независимо от изображения. Основная кнопка вынесена под карточку в нижнюю
доступную зону; единое кольцо видно до запуска, но отсчёт стартует только по нажатию.
Декоративная орбита главной вращается медленно, второе кольцо меняет прозрачность; оба движения
отключаются при `prefers-reduced-motion`. Скроллбар получает тёмную тему.
Пикс удаляется с результата и из первичной анкеты. Переход между заданиями начинается только после
успешного ответа API.

### 10. Замена хранится append-only и поддерживает текущий/следующий индекс

`session_task_substitutions` хранит сессию, индекс, исходный/новый task ID, причину, operation ID и
время. Assignment неизменяем. Endpoint требует `Idempotency-Key` и `If-Match`; `effectiveSteps`
вычисляются сервером. Причины: `not_now`, `not_helpful`, `cannot_do`. Последняя отдельно предлагает
обновить профиль, но не меняет его молча.

### 11. Новый каталог ограничен двумя кандидатами

- `cool_wash` — умыться прохладной водой, нужен `wash_access`, минимум 20 секунд;
- `pushups` — отжимания по своему уровню: от пола либо с колен, нужны разрешённое активное движение
  и свободное место, плановый интервал 20–30 секунд после перехода `sit_edge` или разминки.

Третий кандидат откладывается до пилотных данных. Старые профили по умолчанию не разрешают новые
действия; активные v7-сессии не меняются.

### 12. Слабый результат создаёт отдельный recovery

При `postRating - baseline <= 1` один раз предлагается дополнительный раунд до 90 секунд. Он имеет
`session_kind=recovery`, ссылку на primary и отдельный outcome. Primary analytics его не включает.
Отказ спокойный и окончательный; follow-up остаётся ровно один после последнего принятого этапа.

### 13. Лаборатория сравнивает сочетания только на достаточных личных данных

Аналитика хранит фактическую последовательность, контекст, длительность и замены. Сочетание получает
рабочую оценку только после повторов в сопоставимом контексте и временном бюджете; UI показывает
размер выборки и не делает причинных или медицинских выводов. До достаточных данных система
продолжает контролируемое разнообразие, а не закрепляет случайно удачный единичный протокол.

### 14. Визуальный слой для первого входа, главной и настроек

Первый визуальный этап использует существующие React-компоненты и клиентские API без нового
framework, datastore или серверного контракта. Стили размещаются в ограниченных классами правилах:
тёплый почти чёрный фон, светлая типографика, янтарные акценты и тонкие контуры. На главной CSS/SVG
рисует декоративную орбиту вне интерактивной области; её нет на внутренних экранах. При
`prefers-reduced-motion` декоративное движение выключено. Растровые макеты служат ориентиром, но
тексты, даты и несуществующие элементы из них не переносятся без сверки с кодом.

Порядок первого входа остаётся legal gate → четыре страницы анкеты → главная. Каждая страница
анкеты показывает один вопрос, прогресс и постоянные действия «Назад»/«Далее»; черновик сохраняется
при возврате, единственная запись происходит на финальном шаге. В настройках те же поля
редактируются через существующий профиль. Названия режимов «Короткий», «Средний», «Длинный» и
примерное время 2/5/10 минут меняют только UI-формулировку, не значение API.

Главная сохраняет запуск, серверные показатели и прогресс до семи завершений. Цель показывается
только после получения сохранённого текста владельца; отсутствие или ошибка загрузки не подменяется
примером из макета. Настройки сохраняют напоминание на каждый день, включая статус доставки,
ограничения заданий, жизненную цель, рутину, Pro-карточку, ссылки на документы и удаление профиля.
Выбор дней недели из изображения не добавляется: текущий API хранит ежедневное время и часовой пояс.

Стартовое ожидание, ошибка входа, legal gate и публичные `/privacy`/`/terms` получают ту же
типографику и оформление. Содержание документов, версии согласия, оператор/контакт, ссылки,
юридическая блокировка до принятия и возврат внутри Telegram остаются прежними. В этом этапе
статистика и активный протокол функционально и визуально не перестраиваются.

### 15. Визуальный слой активного протокола

Второй визуальный этап использует те же цвета и типографику для исходной и итоговой оценки,
когнитивных и физических заданий, просмотра назначенного порядка, замены, результата и recovery.
Кнопки протокола и звука находятся в одном ряду. Карточка задания занимает высоту своего содержимого,
а основное действие остаётся доступным на типичном мобильном экране; увеличенный системный шрифт
допускает прокрутку. SVG-подсказка движения показывает смену поз и сохраняет статичную альтернативу
при `prefers-reduced-motion`. Результат показывает только фактические оценки и назначенные задания.
Никакие таймеры, пороги, версии команд и серверные переходы при этом не меняются.

### 16. Визуальный слой статистики

Статистика продолжает тёплую тёмную систему без орбиты внутренних экранов. Верхняя карточка
показывает только рассчитанное среднее изменение бодрости и размер выборки; при загрузке и нуле
наблюдений вместо числа стоит прочерк. «Следующий шаг» остаётся видимым при любом состоянии данных.
До семи завершённых пробуждений его карточка показывает прогресс первого общего профиля. Отчёт
появляется по прежнему правилу после трёх; до порога выводится нехватка данных. Профиль, детали
истории, исследовательские опросы и их серверные правила сохраняются. На 320–390 px страница
прокручивается по вертикали без горизонтального выхода, а интерактивные элементы остаются доступны.

## Risks / Trade-offs

- [Обязательная анкета увеличивает отток] → 2–3 коротких шага, прогресс, безопасные defaults и
  редактирование позже.
- [Пять минут становятся субъективно длинными] → показывать ожидаемое время и позволять менять режим
  в настройках, но не выдавать короткий протокол за пятиминутный.
- [Безопасный каркас воспринимается как универсальный рецепт] → явно объяснять, что задания и порядок
  подбираются и сравниваются персонально.
- [Предпросмотр увеличивает когнитивную нагрузку] → одна строка следующего шага; полный протокол
  только в sheet.
- [Home Screen API отсутствует] → ручная инструкция и отсутствие повторного показа после отказа.
- [Звук раздражает или блокируется] → default-off, mute на каждом шаге, визуальный fallback.
- [Анимации ухудшают доступность] → inline SVG/CSS, lazy loading и `prefers-reduced-motion`.
- [Замены снижают сопоставимость] → хранить исходный/эффективный порядок и исключать нарушенные
  factor comparisons.
- [Recovery выглядит как давление] → одно необязательное предложение с точной длительностью.
- [Новый state усложняет reconnect] → versioned/idempotent команды и E2E закрытия на переходах.

## Migration Plan

1. Выпустить исправление прямого входа и компактный shell без изменения схемы.
2. Выпустить обязательную первую настройку, `sit_edge`, новый планировщик времени и Home Screen
   prompt после mobile smoke.
3. Последовательно включать личную цель/калибровку, визуальный shell, звук/анимации и каталог v8.
4. Добавить forward-only migration для substitutions, experience snapshot и recovery, проверить всю
   цепочку на отдельной disposable PostgreSQL.
5. Включать замену, recovery и анализ сочетаний только для пилотной когорты после сравнения
   completion/drop-off/follow-up.

Rollback отключает экспериментальные flags и возвращает прежний web/API-код. Схема и append-only
события не откатываются; уже начатая сессия выполняется по сохранённой версии протокола.

## Актуальные defaults и повтор AI

Решение владельца от 2026-10-04 заменяет прежние выключенные production defaults для каталога, замены и recovery: отсутствие переменных включает функции и на API, и на web. Явное false отключает функцию; парные overrides web/API должны совпадать. Combination analytics остаётся отдельным выключенным пилотом. Серверные ограничения возможностей, eligibility, ownership и версии сохраняются. Неудачный deterministic-fallback кешируется только до следующей локальной полуночи; успешный отчёт используется при неизменных агрегатах. Сохраняется не более одной попытки provider в локальный день. Диагностика содержит только фиксированную причину и HTTP status, без сообщения ошибки, тела ответа, ключа, ID или агрегатов.
